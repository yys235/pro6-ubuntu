# Pro 6 原厂启动链与 Root 入口分析

本轮仅采集、分析，未申请 Root、重启或刷写。

## 设备上的官方 Root 入口

ADB 包管理信息实际列出：

- `com.android.settings/com.meizu.settings.MzSettingsActivity$RootPermissionSettingsActivity`，action 为 `android.settings.ROOT_SETTINGS`。
- `com.android.settings/com.meizu.settings.root.FlymeRootRequestActivity`。
- `com.meizu.account/com.meizu.root.OpenSystemRightActivity`，action 为 `com.meizu.action.ROOT`。

执行 `am start -a android.settings.ROOT_SETTINGS` 成功，随后 dumpsys 确认前台是上述 RootPermissionSettingsActivity。没有自动点击或提交任何申请。入口存在不证明服务端在线、账号满足条件或 Root 可用。原始证据见 evidence/settings-package.txt 和 account-package.txt。

通过 HTTP Range 读取 ZIP 尾部、中央目录和选定条目，解压了 boot.img、lk.bin、scatter.txt、build.prop 和 updater-script。后续独立计算确认这 5 个条目的长度和 CRC32 均与 ZIP 中央目录一致，结果保存在 evidence/zip-entry-verification.json。没有下载完整 ZIP，未完成完整包 MD5或签名信任验证。CRC32不是真实性验证；提取物只用于离线分析，不能称为已经验证可刷的本机备份。

`Meizu/meizu_PRO6/PRO6:7.1.1/NMF26O/1594347230:user/release-keys`

## boot.img

- 解压大小：10271616 字节，小于本机 16MiB boot 分区。
- SHA256：`9BA16AF32078C91E4305A106575B64A5AE171BACA8741C6D44171B5069CE178E`。
- 偏移 0 为 `ANDROID!`；page_size=2048。
- kernel_size=7888477；ramdisk_size=2374156；second_size=0。
- cmdline：`bootopt=64S3,32N2,64N2 buildvariant=user`。
- ramdisk 位于偏移 7890944，以 gzip 开始；解压为 newc CPIO，解析到 67 个条目。
- 含 init.mt6797.rc、init.mt6797.usb.rc、init.usb.configfs.rc、fstab.mt6797、verity_key 等。
- fstab 将 system 和 userdata 挂载为 ext4；userdata 有 `encryptable=.../metadata`。这不说明本机当前一定启用了加密。
- fstab 中 system 行未见 verify 标志，但 ramdisk 中存在 verity_key。不能据此声称启动签名验证已关闭。

- SHA256：`1418F707BCC147F7914975334EAA87E34D807B0BD218A4FBA2FB5F24D0F418B5`。

## 原厂更新脚本揭示的恢复边界

包中有 boot、LK、preloader、TEE、基带和系统数据；脚本会更新双份 LK、SCP、TEE、preloader 并切换活动副本。它不是只有 system 的普通包。

但 ZIP 目录未见独立 recovery.img，scatter.txt 只有简短地址列表，没有完整 SP Flash Tool scatter 结构。因此不能把这个 ZIP 直接称为 BROM 救砖套件，也不能把其中 scatter.txt 直接交给刷机工具。

## 后续优先级

1. 查看手机当前打开的官方 Root 权限页面，确认可见说明、账号/申请要求和是否提供开关。账号验证由用户完成；本轮不自动授权 Root。
2. 验证下载条目 CRC32及来源记录；补充匹配 recovery/可恢复入口。
3. 有可靠读取能力后备份本机 boot/recovery/GPT与独有校准分区，核对 boot 是否与原厂包一致。
4. 分析 LK 的 fastboot 命令注册、seccfg 读取及签名校验，确认能否启动修改 ramdisk。芯片级 mtkclient 支持不能代替这一步。
5. 通过启动门槛后，第一目标为最小 Linux initramfs + USB shell/网络。原生目标仍保留，不用 chroot 成功替代原生启动成功。

## 后续只读核查

- 原厂 gzip 内核成功解压，大小 18612952 字节；内嵌 Linux 版本、构建时间与实机 uname 一致。
- 未找到 IKCFG_ST 内嵌配置标记，本机 /proc/config.gz 也不存在；目前仍没有完整内核配置。
- 内核镜像有 kexec 字符串，但本机 /sys/kernel/kexec* 和 /proc/sys/kernel/kexec* 均不存在。不能把字符串当作 kexec 可用证明。
- ramdisk 的 init.usb.configfs.rc 有 rndis 和 rndis,adb 配置，本机 /sys/class/udc 列出 musb-hdrc。这为最小 initramfs 的 USB 网络研究提供了线索，尚未在独立 Linux 启动中验证。
- 本机读取：ro.flyme.root.state=0、ro.oem_unlock_supported=1、sys.oem_unlock_allowed=0；settings global 中 oem_unlock_allowed 返回 null。含义以属性和具体实现为限，不能视为 bootloader 已解锁或通用解锁命令可用。
- /sys/fs/selinux/enforce 返回 0，说明采集时 SELinux 为 permissive，但 Unix 文件权限仍限制 shell 读取 root:system、0640 的 boot 块设备。SELinux permissive 不等于 root。
- 已截取当前 Root 权限管理页进行本地查看，页面列出应用权限询问状态；这不是 Root 已成功开启的证据。截图含安装应用信息，仅保存在本地 evidence/root-settings-screen.png，不对外发布。

当前仍可继续的离线工作是 LK 静态分析、匹配源码和 recovery 材料调查；需要本机权限或改变启动状态的步骤要与这些研究结论区分。

## LK 命令注册与启动签名：进一步证据

使用本地 Capstone 5.0.9 对原厂 LK 做离线反汇编。512 字节 MTK 头之后是 ARM 入口代码；重定位代码中的常量表明正文运行基址为 0x46000000。后续主要代码为 Thumb。

在 0x460233ec 起的 fastboot 初始化代码中，命令名传入同一注册候选函数 0x46022f30；该函数与发布 getvar 变量的函数 0x46022f6c 不同。对代码区域进行线性 Thumb 解码找到 13 个直接 BL 调用，均位于此初始化段：

`getvar:`、`signature`、`flash:`、`erase:`、`continue`、`reboot`、`reboot-bootloader`、`download:`、`oem reboot-recovery`、`oem append-cmdline`、`oem off-mode-charge`、`oem scp_status`、`oem usb2jtag`。

该段未注册 `boot`、`oem unlock`、`flashing unlock`。这是针对本固件的静态证据，比只搜索字符串更强；仍不排除间接调用、其他解码模式或尚未分析分支，不能当作动态实测。原始反汇编、调用点和名称分别保存在 lk-fastboot-registration.txt、lk-register-callers.json、lk-registration-names.json。

作为对照，M3 Note 的公开 LK 源码将 `oem unlock` 和 `boot` 放在 MTK_SECURITY_SW_SUPPORT / MTK_SEC_FASTBOOT_UNLOCK_SUPPORT 条件编译块内。它解释一种可能原因，但不是 Pro 6 的源码或构建配置证据：
https://github.com/lanlanpy/m3note_android_bootable/blob/master/bootloader/lk/app/mt_boot/fastboot.c

### boot 尾部不是可随意丢弃的空白

Android 头所述 kernel/ramdisk 按页对齐后共 10266624 字节；文件另外有 4992 字节尾部。第一段为 1320 字节 DER BootSignature：

- AlgorithmIdentifier 为 sha256WithRSAEncryption。
- 签名属性包含目标 `/boot` 和长度 10266624。
- 使用其中内嵌 X.509 证书公钥，对“前 10266624 字节 + DER 签名属性”执行 RSA PKCS#1 v1.5 / SHA256 验证，结果通过。
- 证书 SHA256：8ad127abae8285b582ea36745f220ab8fe397ffb3b068df19ca22d122c7b3b86。
- 后续还出现 MTK 头魔数及 cert1 名称，相关证书/校验链仍未完整分析。

这个数学验证仅证明签名与内嵌公钥和内容一致，不证明证书受本机信任，更不证明修改后可启动。只重打包 ramdisk 会改变上述签名覆盖的数据，不能以标准 Android boot 头为由忽略签名层。

后续已确认此内层证书和私钥是公开 AOSP verity 测试密钥，并已逐字节重现原厂内层签名；因此内层可以重签。真正尚未确认的是外层 MTK cert1/cert2 的镜像验证及写入/恢复权限，详见《签名分层与下一步-2026-10-18.md》。

可复验脚本：项目根目录 verify_firmware_evidence.py；依赖 Python cryptography，仅读取本地文件。本轮实际执行退出码 0，5 个提取条目 CRC32/长度和 boot 内嵌密钥签名检查通过；输出见 evidence/verification-result.json，明确 trust_chain_verified=false。

### DTB 已单独提取

kernel gzip 数据消耗 7774209 字节，其后恰好是 114268 字节 DTB（kernel-dtb-0.dtb）。DTB 的 model=MT6797、compatible=mediatek,MT6797，chosen 中有面板名 d53g_fhd_dsi_cmd_sec。设备树仍可能由 LK 在启动时修改，chosen 中静态 initrd 地址/长度不可当作实际运行参数。

后续制作实验 boot 时必须保留并正确处理此附加 DTB；只替换 gzip 内核而遗漏 DTB 会丢失板级硬件描述。

### 对原生 Linux 路线的影响

当前最有依据的第一阶段仍是复用原厂内核与匹配 DTB、替换最小 initramfs，但前提是先解决签名接受和可恢复写入。现有证据不支持直接执行 fastboot boot，也不支持通过一个通用 OEM 解锁开关完成全部解锁。

后续已经用本机可读的 recovery-from-boot.p、recovery-resource.dat 和匹配原厂 boot 在电脑上重建 recovery，header ID 与本机预期匹配、内嵌签名校验通过，详见《原厂Recovery重建-2026-10-18.md》。原厂 recovery 配置没有开放普通 ADB shell；实际进入/返回和写回通道仍未验证，恢复门槛尚未全部满足。
