# 签名分层核查与当前推进点

## 本轮新增证据

原厂 boot 的 BootSignature 内嵌证书 SHA256，与公开 AOSP verity 测试证书完全一致：

`8ad127abae8285b582ea36745f220ab8fe397ffb3b068df19ca22d122c7b3b86`

从 LineageOS 的 AOSP 构建源码镜像获取公开 verity.x509.pem 和 verity.pk8，确认私钥公钥与证书匹配；使用这把公开测试私钥，对原厂 boot 的签名覆盖数据重新执行 RSA PKCS#1 v1.5 / SHA256 签名，输出与原厂 256 字节签名逐字节相同。

来源：
https://github.com/LineageOS/android_build/tree/cm-14.1/target/product/security

证据：evidence/public-key-comparison.json。此处的私钥是公开开发测试密钥，不是用户或厂商秘密。下载文件以 public-aosp- 为前缀，避免与本机身份密钥混淆。

**修正后的结论：内层签名可以使用已知公开测试密钥重现，不能把内层签名本身视为不可跨越的门槛；但是外层验证与写入权限尚未解决。**

## 外层 MTK cert1 / cert2

从 boot 尾部独立提取：

| 部分 | boot 内文件偏移 | DER 长度 |
|---|---:|---:|
| cert1 数据 | 10268464 | 1685 |
| cert2 数据 | 10270672 | 932 |

它们的结构带厂商自定义字段，不能被标准 X.509 完整解析器直接接受。独立遍历 DER 后，找到三个 RSA-2048 SubjectPublicKeyInfo：cert1 中有两个，cert2 中有一个；cert2 公钥与 cert1 的第二个公钥相同，均不同于内层 AOSP verity 公钥。

对外层证书的原始 TBS 字节和 BIT STRING 签名执行验证：

- cert1 用其第一个公钥执行 RSA-PSS / SHA256 验证，通过。
- cert2 用 cert1 的第二个公钥执行 RSA-PSS / SHA256 验证，通过。
- 算法参数包含 SHA256、MGF1-SHA256、32 字节 salt。

证据：evidence/mtk-cert-public-keys.json、mtk-cert-signature-results.json、cert1.der、cert2.der。

这些结果证明内部签名数学关系，尚未验证 cert1 的根公钥是否等于本机实际信任根。后续已确认 cert2 的镜像散列字段与覆盖范围，见下文。公开 verity 私钥不能签出这两层的有效厂商签名。不得把“能重签内层”描述成“已经可以刷 Linux”。

公钥原始模数也出现在 lk.bin 尾部证书区，不能据此声称它们已被确认硬编码在验证代码中。

## Root 页面核查状态

只读拉取 Settings.apk，资源和 DEX 字符串确认包含 RootRequestActivity、isRootPermissionOpened 等代码及 Root 页面资源。

尝试打开 FlymeRootRequestActivity 时手机处于 Asleep、显示关闭，截图为全黑；前台记录仍指向 RootPermissionSettingsActivity。不能据此推断 Root 服务器停用、申请失败或页面无效。没有唤醒解锁、提交账号、同意授权或重启手机。

当前需要用户解锁手机并查看实际 Root 开启入口。Root 权限管理中列出应用及“询问”状态，不等于系统 Root 已开启；现有属性仍为 ro.flyme.root.state=0，shell 非 root。

## 推进顺序

1. 用户解锁手机，检查官方 Root 开启/申请页面的实际说明。账号或验证码由用户自行输入。
2. 若能取得用户授权的 Root，先做本机只读分区备份并回读验证，不立即刷入修改 boot。
3. 进一步确认外层镜像校验和可恢复写回通道，必要时再研究 BROM 读取；不套用其他机型的 seccfg/LK/preloader。
4. 上述条件满足后，才构建原厂内核、匹配 DTB 和最小 Linux initramfs 的实验镜像。

本轮手机未刷写、未提交 Root、未修改 OEM 解锁开关。原生 Linux 尚未启动，目标继续保留。

## 外层散列覆盖范围已核实

依据 liblk 的证书格式说明，cert2 第一内部序列的第10项是 image_hash，第14项是 header_hash（从0计数；BIT STRING 值跳过 unused-bits 字节）。

参考：
https://github.com/R0rt1z2/liblk/blob/master/liblk/structures/certificate.py
https://github.com/R0rt1z2/liblk/blob/master/liblk/structures/partition.py

对本项目实际文件独立计算，全部匹配：

| 文件 | header_hash覆盖区间 | image_hash覆盖区间 |
|---|---|---|
| boot.img | [0,2048) | [2048,10266624) |
| recovery-reconstructed.img | [0,2048) | [2048,16248832) |
| lk.bin | [0,512) | [512,325276)，尾部补零至16字节对齐 |

半开区间，不包含右端点。boot 的两个实际散列：

- header：acfc29d5c8bb2e07713487cf40e5efabe7bcf0002803488a6b52c9f980ad0dac。
- image：1a18f6603717083dc0144522e3ad8f20cec7dc53733a85f61e5da2d42f590a5b。

可重复的只读脚本为 verify_outer_certificates.py。本轮执行退出码0，三个文件的头部散列、载荷散列、cert1内部签名及cert2签名均通过；结果见 evidence/outer-certificates-verification.json。device_trust_anchor_verified 仍为 false。

结论：内层 AOSP BootSignature 位于 image_hash 覆盖区间之后，但 ramdisk 和内核均在外层 image_hash 覆盖区间内。修改 ramdisk 后重签内层，不会修复外层散列/签名关系。

lkpatcher 新源码提供 cert2 parser 绕过构造方式，但本机厂商解析器是否受影响、启动链是否允许、能否恢复写回均没有证据；只阅读源码，没有执行其补丁/绕过功能或生成待刷 LK。不能将通用工具说明当成本机可用结论。
