# 原厂 Recovery 重建结果

本轮通过正常 Android ADB 只读取得系统文件，在电脑上重建镜像，没有重启手机或写分区。

## 输入与方法

- boot.img：之前从官方匹配固件提取并校验的文件。
- 手机 `/system/recovery-from-boot.p`：3806216 字节；IMGDIFF2，3 个分块。
- 手机 `/system/etc/recovery-resource.dat`：1829861 字节，作为第二块解压后的 bonus 数据。
- install-recovery.sh 存在但当前 shell 无读取权限；本轮没有修改权限。

IMGDIFF2 按 AOSP 算法重建：普通块应用 BSDIFF；DEFLATE 块先解压原 boot 中的 ramdisk 数据、附加 bonus、应用 BSDIFF，然后按补丁指定的 zlib 参数压缩。资源文件长度恰好补足源解压数据要求：5747712 + 1829861 = 7577573。

算法参考：
https://github.com/LineageOS/android_bootable_recovery/blob/cm-14.1/applypatch/imgpatch.cpp

可重复脚本：`reconstruct_stock_recovery.py`。本轮执行退出码 0，两次重建 SHA256 一致。脚本只读本地输入，写 evidence 下的本地结果，不调用 adb、不访问手机块设备。

## 输出

- 文件：evidence/recovery-reconstructed.img。
- 大小：16253824 字节，小于本机 recovery 分区的 30MiB。
- SHA256：b4011092b2eaa08e92951610cf920abaf050a445bb66c36955a939b3b2a1f0d3。
- header ID：057229c01dc76f513aeedda5fe47dcda5310bb3b。
- 按 Android boot v0 规则重算 kernel/ramdisk/second 的 SHA1 ID：与 header ID 相同。
- 手机 ro.expect.recovery_id 前20字节：与上述 ID 相同，其余为零。
- 镜像内核大小 7888477；ramdisk 大小 8355886；page_size=2048。

三者一致证明重建内容与手机预期 recovery 标识匹配。它不代替当前 recovery 分区回读，也不证明 BROM/fastboot 写回通道已经可用。

## 签名验证

镜像有效载荷按页对齐后为 16248832 字节；尾部 BootSignature 的目标是 `/recovery`，长度字段与有效载荷相符。

用其中内嵌证书公钥对“有效载荷 + DER签名属性”执行 RSA PKCS#1 v1.5 / SHA256 验证，通过。证书指纹与原厂 boot 相同。证据：evidence/recovery-signature-verification.json。

尚未验证完整厂商启动信任链和后续 MTK 证书封装，不将这项校验称为可恢复性实测。

## 恢复环境的限制

解压 recovery ramdisk，解析到 763 个 CPIO 条目。包含 sbin/recovery、system/bin/recovery_service、busybox 相关材料和 recovery.fstab。

但没有找到独立 adbd 文件；init.rc 的 service adbd、FunctionFS adb、console 服务等定义被注释。USB 的 storage,adb/mtp,adb 触发器实际只设置 mass_storage 或 mtp。

因此不能把原厂 recovery 当作已经具备 root ADB shell 的救援系统。即使能进 recovery，也不能直接复用 L36h 的 SSH/ADB 镜像传输和分区备份流程。它能否安全返回 Android、是否提供可用更新入口，仍需后续在用户无正在进行的手机任务时验证；本轮未进入 recovery。
